Cakify 四候选 Windows 基准报告

报告日期：2026-08-17（Asia/Shanghai）
测试 commit：40209896dca0009b747efc51ac885bed32b81f25
仓库状态：PRIVATE

结论：对于 Windows-first、启动快、常驻内存低的目标，GPUI + Rust 是第一选择。它的整棵进程树空闲 Working Set 中位数为 42.016 MiB，ready 中位数为 113.745 ms。Avalonia 是成熟度优先的回退方案；Flutter 适合跨平台优先；Tauri 的包体最小，但 WebView2 进程组使运行时内存最高，不应被当成低内存方案。

GPUI 仍需通过中文 IME、无障碍、Markdown 和物理 Windows 硬件门禁后才能进入产品主线。当前推荐采用“GPUI 主线 + Avalonia 可回退”的决策结构。

候选判断

GPUI + Rust

四项运行时指标均领先，没有 WebView2 或托管 runtime 进程组，最符合低内存目标。主要风险是 pre-1.0 API、文档成熟度、中文 IME 和无障碍。当前壳的输入区仍需产品级实现。

Avalonia + C# + Rust

控件和 TextBox 输入路径成熟，适合设置页、审批弹窗和无障碍语义；代价是约 126 MiB 空闲 Working Set 和约 129 MiB 发布目录。窗口句柄探针三轮误报 false，但截图显示窗口可见，下一轮要改 UI 自动化探针。

Flutter + Rust

UI 和跨平台能力完整，发布目录约 26 MiB；Windows engine 使空闲 Working Set 约 128 MiB、ready 中位数约 1.64 秒，不适合本项目把 Windows 低占用放在第一位的目标。

Tauri + Svelte + Rust

包体约 2.7 MiB，视觉交付速度快；但 WebView2 进程树达到 8 个进程、约 327 MiB Working Set，首轮 ready 达 3 秒。包小不等于运行时内存小。

决策门与工作量

先用 GPUI 做 Provider 设置、会话持久化、流式聊天、工具审批、MCP transport 抽象、取消/重试和错误恢复的纵向切片。粗估 AI 工作量：GPUI 10–15 个工作日，Avalonia 8–12 个，Flutter 9–14 个，Tauri 6–9 个；不含 Actions 排队和人工硬件验证。

  1. 物理 Windows 中文 IME、焦点恢复、DPI、多显示器和无障碍无阻断。
  2. 冷启动到可交互 ready 中位数小于 500 ms。
  3. 空闲整树 Working Set 小于 80 MiB，10k 消息虚拟滚动和流式输出稳定。

GPUI 任一硬门失败时，保留共享 Rust core/协议并切换 Avalonia；不要因为 Tauri 包体最小而选择它。
